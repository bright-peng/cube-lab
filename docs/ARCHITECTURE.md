# 架构与第一性原理

## 1. 正确的问题不是“怎么画一个会转的立方体”

真正需要统一的是三件事：魔方状态如何表示、合法动作如何改变状态、多个视图如何展示同一状态。如果 3D、平面图、求解器各自维护颜色，迟早会出现显示错位或解法与画面不一致。

本项目只有一份 `Uint8Array(54)`：

```js
state[position] = originalStickerIdentity;
```

面次序固定为 URFDLB，每面 9 个格子，按正对该面时从左到右、从上到下排列。贴纸保留唯一身份，而不是只存颜色：这使同一个贴纸在不同视图里都能被追踪和高亮。

八个角块、十二个棱块和六个中心块的结构参见 J Perm 的[三阶入门教程](https://jperm.net/3x3)。外层转动时，中心定义固定颜色。

## 2. 转动是整数坐标上的置换

每个贴纸有位置 `p` 和朝外的法向量 `n`。位置分量取 -1、0、1。例如 R 面法向量为 `(1,0,0)`。转动 R 只作用于 `dot(p, n_R) = 1` 的贴纸；按从外侧观察的顺时针转 90°，即绕朝外轴旋转 -90°。

在初始化时生成六个基本面转动的正向置换表，再合成逆时针与半圈，共 18 个动作。运行时不需要浮点累积来求颜色：

```js
next[permutation[sourcePosition]] = state[sourcePosition];
```

`R⁴ = I`、`R R′ = I` 是最基础的检查。动画可以经过连续角度，但正式状态只在转动结束时提交，因此不会因小数误差而逐渐歪斜。动作记号参考 [WCA Article 12](https://www.worldcubeassociation.org/regulations/#article-12-notation)。

## 3. 为什么不能随便填 54 个颜色

一个角块上的三枚贴纸必须一起移动，棱块的两枚贴纸同理。即使每种颜色都恰好出现九次，也可能是物理上不可达的魔方。

进度导入检查编号排列、中心位置、每个块的完整性、角块手性、角块扭转和为 0（模 3）、棱块翻转和为 0（模 2），以及角/棱排列奇偶性一致。单独翻一条棱、扭一个角或交换两个棱的非法输入都在测试中被拒绝。

当前没有手工涂色入口，导入的是本项目导出的编号状态，不是照片或任意 54 字符颜色串。

## 4. 魔方是状态图，不是最大流问题

用户粘贴的 flow network 介绍含容量、源点、汇点和流量守恒；这些不是当前魔方求解需要的模型。

这里的节点是合法魔方状态，边是一次合法动作；起点是当前状态，目标是复原状态。可寻找路径，也可把某个能保持已完成区域的公式当作一条宏边。

直接搜索整个状态空间不适合这个学习工具。我们把目标划分为七个带有明确后置条件的阶段，让每阶段只处理剩余局部自由度。

## 5. 真实的分层求解器

求解函数只接收当前状态，**不读取用户的打乱历史**。每个公式都有预编译的贴纸置换；候选公式组既包括基准公式，也包括逆式与围绕竖轴的工作面重命名版本。这里重命名成固定 U/R/F 坐标字母，而不是要求玩家中途转动整个魔方。

### 前三阶段：模式数据库

把目标四个棱块或角块各自的一枚代表贴纸位置编码为一个整数。从目标状态反向广度优先遍历，保存每个投影状态到目标的距离。

| 阶段 | 搜索的投影 | 本次实际生成的可达状态数 |
| --- | --- | ---: |
| 白色十字 | 四个底层棱块的位置和朝向 | 190,080 |
| 底层角块 | 四个底层角块的位置和朝向 | 136,080 |
| 中层棱块 | 四个中层棱块的位置和朝向 | 26,880 |

随后从当前状态不断选择距离减少一的动作或公式。十字阶段的边是一手外层转动；后两阶段的边是一组公式或顶层调整。**公式长度不同，所以宏边最少不等于手转步数最少。**

### 顶层四阶段：小型公式图搜索

黄色十字使用边朝向公式；黄顶角朝向使用 Sune；角块位置使用 T-perm；最后的棱块位置使用 U-perm。每一阶段只保留对其目标必要的状态键，使用广度优先搜索寻找适用宏序列。

每完成一阶段，检查阶段目标成立；完整结果再从输入状态回放一次，必须回到复原状态才允许显示给用户。这是“生成后验证”，不是仅相信搜索输出。

没有使用 Kociemba 或其他第三方求解库。这里的取舍是可解释的阶段结构，而不是紧凑的最短解。分层学习思路参考 [Cube Academy](https://www.cube.academy/how-to-solve-a-rubiks-cube)，动作与常用公式可对照 [SpeedCubeDB](https://www.speedcubedb.com/a/3x3)。

## 6. 三个视图为什么能联动

3D 渲染器从同一份状态读取颜色，用相机基向量和透视除法投影 cubie 表面，按深度绘制可见多边形。它不是静态图片，也没有加载外部渲染库。

SVG 展开图直接把相同的 54 个位置映射到六个九宫格。环形视图也一一对应这 54 个位置，但采用六个同心环、每圈九区段的编码。它不保留真实相邻关系，不冒充标准立体投影。

点选任一视图中的贴纸，会记下它的原始编号，而不是当前格号；此后转动魔方仍可追踪该贴纸。为了看清环内编号，二维视图提供放大弹窗。

## 7. 交互与资源控制

- 同一时刻只提交一个层转动；播放中的手动修改入口被禁用。
- 暂停等当前转动完成，前进和后退对应原动作与逆动作。
- 播放会话编号阻止快速暂停/恢复产生旧循环并行。
- 求解放在 Worker，结果返回后仍在 UI 线程验证；计算超时会终止 Worker 并保留当前状态。
- 3D 仅在状态、相机或动画改变时请求绘制，不常驻无意义的全速渲染循环；像素比上限为 2。
- 减少动态效果的系统设置会关闭层转动动画。
- 本地存储失败会提示导出进度，不把保存失败当作保存成功。

## 8. 为什么不先上后端框架

这个版本没有多人共享状态、账号、计费或云端求解需求。将游戏放在纯静态网页里，可避免服务器成本和登录流程，并使代码更容易离线验证。后续确需排行榜或跨设备同步时，可在 `core.js` / `solver.js` 不变的前提下增加 API；没有必要为了显示一个魔方先启动数据库和后台服务。
